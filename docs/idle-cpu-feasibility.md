# 空闲 0% CPU：现状、可行性评估与代价

> 本文只做**现状与可行性评估**，不是实施方案。若决定动手，另出 `docs/plans/NN-*.md`。
> 数字均为本机实测（i5-13600K，标称 3494 MHz；**release 构建**；164 图标 / 5 栅栏 /
> 1 个链接栅栏＝桌面）。
>
> **2026-09-13 修订**：初版把那个「平台后台线程」判为 WinRT/COM 常驻线程，并据此给出头条结论
> 「为省电不值」。复核后**该归因被推翻**（它是 NVIDIA 用户态驱动线程），另有四处数字与两处判据
> 被修正。明细见文末《修订记录》；错误处已就地改写，未改动处不再标注。

## 0. 结论先行

| 问题 | 结论 |
| :-- | :-- |
| 现在空闲真的是 0% 吗？ | **不是**。进程级约 **0.15% ~ 0.25%**（真实周期计数）。注意**同一台机器不同时刻能差近 2 倍**——这不是一个常数，引用时必须带环境 |
| 这 0.15%~0.25% 是谁的？ | 我们的 4s 库同步心跳约 **0.10%~0.14%**；**NVIDIA D3D11 用户态驱动线程**约 **0.05%~0.09%**；第三方 Shell 扩展 / Shell 线程池约 **0.02%~0.07%** |
| 我们的代码干净吗？ | **主线程在空闲期已经是精确 0**——心跳之外一次都不醒（本轮动画改造的直接成果，复核成立） |
| 能做到真正的 0% 吗？ | **进程级不可达**（GPU 驱动线程与第三方 Shell 扩展线程都不是本工程关得掉的）；**主线程级已达成** |
| 值不值得做？ | 「**为省电**」的收益**未经任何验证**（见 §2 L3）；「同步延迟 4s → 近乎实时」值得。建议先改文档措辞 + **降单次成本**，事件驱动留待有明确需求 |

## 1. 现状

### 1.1 先纠正一个测量错误

早前用 `GetProcessTimes` 测出「4 秒 16ms、0.39%」，并据此推断心跳耗时 16ms——**这个推断是错的**。

15.6ms 是 Windows CPU **计账的一个时钟量子**（与 §2 的定时器栅格同源）。进程真实只跑了
1~2ms，是否被记成一整个量子，取决于时钟中断有没有恰好落在它运行期间。后果有两个：

- 数值被**高估 2~3 倍**（量子法 0.31%~0.52%，周期法实测 0.124%~0.149%）；
- 尖峰数量逐轮浮动（同一负载下有时记 6 次、有时记 4 次），容易被误读成"负载在变"。

正确工具是 `QueryProcessCycleTime` / `QueryThreadCycleTime`：按上下文切换时的 RDTSC 累加，
精度到周期级，且**不受量子影响**。

> 注意：§5 的回归脚本 `cpu_probe.py` 走的仍是 `GetProcessTimes`（量子法）。它只够看量级，
> **不能用来做「增量相等」这类等式判据**——初版把两者混为一谈，见 §5。

### 1.2 空闲期的全部非零来源

进程共 **60 个线程、176 个模块**。初版称「58 个周期增量为精确 0，只有 2 个在消耗」——
**该快照不可复现**。用同一支 `thread_cycles.py`（10s）在 release 实例上重跑：

| 线程 | 占比 | 入口（模块归位） | 归属 |
| :-- | :-- | :-- | :-- |
| `tid=65004`（窗口线程 = 主线程） | 54.9% | `sylva.exe+0x18DF50` | 我们的代码（全部是 4s 心跳） |
| `tid=11276` | 36.9% | **`nvwgf2umx.dll+0xEB9EB0`** | **NVIDIA D3D11 用户态驱动**（同类线程 30+ 个） |
| `tid=46760` | 7.0% | `uiautomationcore.dll+0x165AD0` | 第三方 Shell 扩展 |
| `tid=37452` | 0.6% | `gdiplus.dll+0xD8AC0` | 第三方 Shell 扩展 |
| `tid=36500` | 0.5% | `SHCORE.dll+0x47710` | Shell 线程池 |
| 其余 55 个 | 0 | — | — |

**合计 0.246%**（85.8M 周期 / 10s @ 3494 MHz）；初版记的是 0.147%。

主线程 500ms 分桶（单位 M 周期）——这一列是全文最硬的证据：

```
时间(s)   主线程 65004
  0.0       0.000M
  0.5       0.000M
  1.0      17.809M  <<<   4s 心跳
  1.5       0.000M
  ...
  5.0       9.118M  <<<   4s 心跳
  7.5       0.000M
```

单次心跳 **14.5M ~ 23.5M 周期（4.2 ~ 6.7 ms）**，波动接近 2 倍（疑与目录项缓存冷热有关）。

折算成占用（3494 MHz）：

| 来源 | 周期/秒 | 占用 | 能否消除 |
| :-- | :-- | :-- | :-- |
| 4s 库同步心跳（主线程） | ~4.7M | **≈0.13%** | ✅ 可消除 |
| NVIDIA D3D11 用户态驱动线程 | ~3.2M | **≈0.09%** | ❌ 非我们所有（换显卡/换驱动就变） |
| 第三方 Shell 扩展 / Shell 线程池 | ~0.7M | **≈0.02%** | ❌ 非我们所有 |
| 其余 55 线程 | 0 | 0% | — |
| **合计** | ~8.6M | **≈0.246%** | — |

#### 1.2.1 「平台线程」的身份：不是 WinRT/COM，是显卡驱动

初版把 `tid=11276` 描述为「看起来像 WinRT / COM / DirectX 的常驻工作线程，未确认身份」，
并据此推出「要消掉它，等于放弃 WinRT 合成」。**该推断是错的**，且不需要 ETW 就能证伪：

- `OpenThread(THREAD_QUERY_INFORMATION)` → `NtQueryInformationThread(h, 9 /*ThreadQuerySetWin32StartAddress*/, ...)`
  取入口地址，再枚举模块归位 → **`nvwgf2umx.dll+0xEB9EB0`**（NVIDIA D3D11 用户态驱动），
  且**同进程内同类线程 30+ 个**，另有 `nvgpucomp64.dll`（94 MB）在列。
  注：`THREAD_QUERY_LIMITED_INFORMATION` 会被拒（`0xC0000022`），必须用 FULL 权限。
- 顺带：`GetThreadDescription` 能读出 Rust `thread::Builder::name` 设的线程名——
  本进程 60 个线程里只有 2 个有名字（`main`、`tracing-appender`），其余全是驱动/Shell/COM 原生线程。

**两个后果：**

1. 「关掉它＝放弃实时模糊」是**假二分**。它是 GPU 驱动线程，与 WinRT 合成没有因果关系；
   换一张显卡、换一个驱动版本，这批线程的数量与负载都会变。
2. 它**不是「无周期性」**。初版这么写，把持续负载描述成了偶发尖峰。50ms 分辨率实测：
   **60/60 个桶全部非零**，均值 163K 周期（120K ~ 225K），即连续或高频负载。

#### 1.2.2 「60 个线程」也不是我们的架构常数

模块表里有一批**第三方 Shell 扩展**被加载进本进程：`IDMShellExt64.dll`、`qingnse64.dll`、
`msiltcfg.dll`，以及某个 .NET 扩展带进来的 `clr.dll` + `mscorlib.ni.dll` +
`System.Windows.Forms.ni.dll` + `uiautomationcore.dll`。它们各自带来自己的线程。

所以「线程数 60 / 平台底数 0.05%」是**本机环境相关的观测值**，不是架构属性。
换台机器、少装一个 Shell 扩展、换一块显卡，这组数字都会变。

### 1.3 心跳到底在做什么（成本口径已修正）

`OverlayEvent::SyncLibrary`（4s）→ `reconcile_fences`（`crates/app/src/file_ops.rs`）：

1. **`reconcile_library`**：遍历内存里全部图标，但只对**路径位于内部库**的图标调 `Path::exists()`。
   本机库内只有 **5 个**图标（其余 151 个在桌面），所以这里是 **5 次** `GetFileAttributesW`，
   **不是初版说的 155 次**。
2. **`mirror_linked_fence`**（本机唯一的链接栅栏，其 `storage_path` 就是桌面）：
   - `rehome_linked_library_items`：纯内存判断，无系统调用；
   - `list_dir_entries`：对桌面 + 公共桌面各一次 `read_dir`；
   - **`should_mirror`：对每个目录项一次 `GetFileAttributesW`**（用于跳过隐藏/系统文件）；
   - `mirror_existing_paths` / `mirror_converged`：纯内存集合运算（`owned ⊆ all` 与
     `visible ⊆ owned` 两条子集断言）。

即每 4s ≈ **`2 × read_dir` + `O(源目录项数)` 次 `GetFileAttributesW`**。

**这层属性查询就是心跳的全部成本**（独立实测，见 §3.2）：本机桌面 + 公共桌面共 141 个目录项，
141 次 `GetFileAttributesW` 净耗时 **≈ 5.2 ms**，而整个心跳实测 4.2 ~ 6.7 ms——两者吻合。

**这是本评估里唯一会随数据量恶化的问题**，且恶化系数是**目录项数**，不是「图标数」——
一个装着 1 万个文件的链接文件夹，比 1000 个图标更糟。另外 `read_dir` 自身就是每项一次系统调用，
所以这条路**不可能优化成 O(1)**，只能砍掉叠加在它上面的那层 `GetFileAttributesW`。

> 2026-09-13 的 `8f5f8f7` 已经修掉了此前的一个真实缺陷：旧代码用「集合相等」做收敛判据，
> 一旦某个已归属文件被外部置为隐藏/系统属性，判据**永久不成立** → 每 4s 白跑一遍全量注册 +
> 全量 `exists()` 探测。现在换成两条子集断言，已归属项不再被逐个 stat。

## 2. 真正的空闲 0% CPU：可行性

先分清三个层次，否则讨论必然鸡同鸭讲：

### L1 · 主线程空闲 0 —— **已达成**

心跳之外，主线程每一桶都是 `0.000M`。消息循环是纯阻塞 `GetMessageW`，动画结束后
`CancelWaitableTimer` + `ANIM_TIMER_ARMED = false`，没有任何周期性唤醒。这一层不需要改动。

**建议把它固化成回归断言**（`SYLVA_AUTOSTOP_MS` 那套基础设施已经够用）：判据用
`QueryThreadCycleTime` 看主线程分桶，非心跳桶必须精确 `0.000M`。否则下次谁顺手加个定时器，
这条铁律会悄悄退化且无人察觉。

### L2 · 进程空闲 0 —— **不可达**（但理由与初版不同）

不是「WinRT 合成器的伴生线程关不掉」，而是：

- **GPU 用户态驱动线程**（NVIDIA UMD，30+ 个）：只要用 GPU 加速就在，与是否用 WinRT 无关；
- **第三方 Shell 扩展与 Shell 线程池**：由我们调用 Shell API（枚举、图标提取）时被拉进进程，
  数量取决于**用户装了什么**，我们既不能卸载也不该替用户决定。

要消掉前者等于放弃 GPU 加速（比"放弃 WinRT 合成"更激进），要消掉后者等于不用 Shell API。
**判定为不可达。**

### L3 · 系统级「不阻止深度节能」—— **未验证，本文最大的方法论缺口**

初版写：「0.049% 看上去微不足道，但一个持续有事的线程会让 CPU 无法进入深度 C-state……
**只要 L2 那 0.049% 还在，我们把自己这份 0.098% 减到 0 也换不回深度 C-state**。」
并让这句**未经任何测量的断言**承载了整篇的头条结论「为省电不值」。

这是本文最该改的地方：**用 CPU 周期占比去推断电池影响，中间隔着一个没有测过的环节。**
要谈省电，就得测省电——C-state 驻留率（或 `powercfg /batteryreport` + 受控 A/B、功耗计），
而不是从 0.05% 这个数字直接跳到结论。

**在测出来之前，正确的表述是：省电收益未验证。** 方向性上「持续有负载会抑制深度节能」大概率成立，
但它成立到什么程度、是否足以否定「削掉我们这份 0.1%」，本文没有证据。

### 2.1 去掉/降低 4s 心跳的技术选项

| 方案 | 机制 | 覆盖 | 主要风险 |
| :-- | :-- | :-- | :-- |
| A. `ReadDirectoryChangesW` | 目录变更事件（可含子树） | 仅本地文件系统可靠 | 网络盘/可移动盘不可靠；缓冲区溢出需全量重扫；句柄随目录数增长；事件风暴 |
| B. `SHChangeNotifyRegister` | Shell 级变更通知 | 覆盖资源管理器操作，网络盘也常生效 | 只通知"发生了什么"，仍需自行对账；对非 Shell 发起的写入可能漏 |
| **C1. 自适应降频** | 保留轮询，条件化改周期 | 全覆盖 | 同步延迟变长 |
| **C2. 降单次成本** | 保留 4s 周期，砍掉每次的系统调用 | 全覆盖 | 见 §3.2（近乎为零） |
| **E. `FindFirstChangeNotification`** | 粗粒度「这个目录变了」信号，收到就重扫 | 同 A（本地盘） | **比 A 简单一个量级**：没有事件流、没有缓冲区溢出、没有事件风暴——收到信号重扫一次即可 |
| D. 保持现状 | 4s 轮询 | 全覆盖、自愈 | 0.13% 常驻 + 延迟 4s |

初版只有 A/B/C/D，漏了 E 与 C2。**E 是 A 与 C 之间的正中间地带**：它把 A 方案里
「溢出、风暴、丢事件」三条复杂度直接消掉（因为不消费事件内容，只消费"变了"这个事实），
代价是变更后仍需一次全量重扫——而重扫路径**本来就要保留**（见 §3.1 第 5 条）。

## 3. 实现代价

### 3.1 方案 A（事件驱动）的具体代价

**必须解决的复杂度：**

1. **句柄与线程模型**：每个被监听目录一个句柄 + 重叠 I/O。可以复用本轮刚建好的
   `MsgWaitForMultipleObjectsEx` 基础设施，在主线程等事件（契合仓库"单线程轻量"约束，
   无需新线程）；但这意味着消息循环的等待对象从 0~1 个变成 0~N 个，循环要重构。
2. **缓冲区溢出**：`ReadDirectoryChangesW` 溢出时事件丢失且**没有"你漏了多少"的信息**，
   只能退化为全量重扫——必须实现重扫路径，等于把现有逻辑换个触发时机，省不掉。
3. **目录消失**：链接文件夹被删、改名、U 盘拔出、网络盘断连，监听句柄会失效，
   需要探测与重建；重建期间又回到轮询。
4. **事件风暴**：批量复制/删除会一口气涌进成百上千条通知，需要去抖与合并，
   否则会把省下的 CPU 一次性吐回去（还会引发大量 `DesktopItem` 构建与重绘）。
5. **正确性风险的性质变了**：今天是"最多延迟 4s，一定自愈"；改事件驱动后是
   "实时，但**可能永久漏**"。漏事件表现为栅栏里留着已被删除的图标——用户可见的 bug。
   因此**无论如何都要保留一条低频对账兜底**（例如窗口可见时 60s 一次），
   也就是说轮询逻辑不会真的被删掉，只是被降频。
6. **仍需全量扫描的时机**：启动、睡眠恢复、监听重建。

**收益：**

- 空闲占用 0.246% → 约 0.11%（**绝对量极小**，且换不回深度 C-state 这件事本身还没验证）；
- 同步延迟 4s → 近乎实时（**这是唯一可感知的收益**）；
- 消除 §1.3 那个"随目录项数线性增长"的隐患。

**方案 E（`FindFirstChangeNotification`）能把上面的 1/2/4 降一档**：不消费事件内容，
只等一个 auto-reset 事件，收到就重扫；3/5/6 仍然存在。

### 3.2 方案 C2（降单次成本）—— 本评估里性价比最高的一步

改动集中在 `crates/app/src/file_ops.rs` 与一处常量，风险极低。两件事可以分开做：

- **C2-a：把 `should_mirror` 的 `GetFileAttributesW` 换成目录项自带属性。**
  `std::fs::DirEntry::metadata()` 在 Windows 上**不额外发系统调用**（std 文档明确保证：
  *"On Windows this function is cheap to call (no extra system calls needed)"*），
  其 `file_attributes()` 就是枚举时 `WIN32_FIND_DATAW` 里那份属性，语义与按路径
  `GetFileAttributesW` 等价。这样每 4s 的 `O(目录项数)` 次系统调用降为 0，
  剩下的 `read_dir` 无法再优化（它本身就是每项一次调用）。

  **实测收益**（本机，141 个目录项，同构循环对照剥离 ctypes 开销）：

  | 项 | 净耗时 |
  | :-- | :-- |
  | 141 次 `GetFileAttributesW` | **≈ 5.21 ms**（单次 ≈ **37 µs**） |
  | 一次 `read_dir` 枚举同目录 | ≈ 0.15 ms（含迭代开销，仅量级参考） |
  | 整个心跳（周期法实测） | 4.2 ~ 6.7 ms |

  单次 37 µs 远高于常规（通常 1~3 µs），疑为 AV 过滤驱动放大——但**心跳总时长与这层
  查询的耗时吻合到几乎相等**，两条独立测量互相印证：**砍掉它，心跳就从 ~5 ms 掉到 ~0.3 ms
  （约 15 倍），并且彻底去掉 O(目录项数) 的恶化系数**。
  这也意味着 §3.2-b 的降频在收益上远不如 C2-a——降频只是把 5 ms 摊到更长的周期，
  C2-a 是把 5 ms 直接变成 0.3 ms。
- **C2-b：条件化降频**（原方案 C）：
  - 无链接栅栏且无可见变化时把周期从 4s 放宽到 30~60s；
  - 按源目录项数动态决定周期（数据量大时反而更该放宽——注意 §1.3 的增长方向）；
  - 窗口不可见 / 系统进入省电模式时暂停。
    这条的基础设施**已经存在**：`crates/app/src/main.rs` 里已有「最近一次用户交互时间」的
    空闲门控（工作集修剪在用），直接复用即可，不必新造。

代价：C2-b 会让同步延迟变长。但"外部删除文件 → 栅栏项消失"延迟 30s 与 4s，体感差别很小。

### 3.3 我的判断

- **为省电**：先别下结论，因为 L3 没测。而且真要省电，**先去查那 0.09% 的 GPU 驱动线程在忙什么**
  ——见下条。
- **最值得查的一件事（本文初版完全跳过了）**：我们主线程在空闲期**精确为 0**，而 GPU 驱动线程
  却**连续**在烧 0.05%~0.09%。这通常意味着「还有东西在按帧提交/轮询」。如果那是我们的合成器
  在空转提交一个未变化的视觉树，那就存在一笔白捡的收益——**而且正好就是初版主动放弃的那个省电目标**。
  初版把它归为「平台天气」然后判不可达，早了一步。
- **为体验**：4s → 实时是用户能感知的，但代价是引入一整套失效/降级/去抖逻辑，
  属于典型"用复杂度换延迟"的交易，应该单独出 plan 并做对抗性审查。
- **该先做的**：C2-a（十几行、零行为变更）+ 改文档措辞。两者都不需要 plan。

## 5. 复现方法

```bash
# 周期级精度测单次心跳（.workbuddy-ai/，测完可删）
SYLVA_AUTOSTOP_MS=70000 ./target/release/sylva.exe &
sleep 12
python .workbuddy-ai/sync_cost.py 120        # 250ms 分桶，输出各桶周期数

# 按线程拆分空闲负载，看是谁在耗
python .workbuddy-ai/thread_cycles.py        # 10s 采样，按线程列出周期增量与占比

# 主线程 vs 指定后台线程的 500ms 细粒度对照（最能说明"谁在轮询"）
python .workbuddy-ai/thread_detail.py 11276  # 参数为待对照的后台 tid

# 线程身份归位（入口地址 → 模块 + 偏移）
python .workbuddy-ai/thread_name.py          # 全部线程的描述与入口

# 当前实例是 debug 还是 release（结论里必须写明，两者不能混比）
python .workbuddy-ai/running_build.py
```

**两个必须知道的坑：**

1. **单实例互斥会让上面的配方静默测错进程。** 互斥检查在 `crates/app/src/main.rs` 中
   `CreateMutexW` 之后立即 `return`，**早于** `SYLVA_AUTOSTOP_MS` 的安装；而脚本用
   `FindWindowW("SylvaOverlay")` 找窗口，会挂到**已在运行的那个实例**上。
   本机常年有实例在跑（本次复核时是 `target/release/sylva.exe`），
   所以：**要么先干净退出已有实例，要么用 `running_build.py` 确认被测进程的身份并写进结论。**
2. **这些脚本都在被 gitignore 的 `.workbuddy-ai/` 下**，clone 出来的仓库里没有它们。
   要让结论可复现，得把脚本收进 `scripts/perf/`，或把关键片段内联进本文。

判据（回归用）：

- **主线程**在非心跳桶必须精确为 `0.000M`（用 `QueryThreadCycleTime`，不是 `GetProcessTimes`）；
- 心跳桶应稳定在 **1 次 / 4s**，单次成本记入趋势，不设等式；
- **进程级总量只做趋势对比，不设等式**——它含 GPU 驱动线程 ±10% 的自然漂移，
  且同一台机器不同时刻能差近 2 倍。初版写的「首尾两个空闲窗口的周期增量应完全相等」
  既不可达（用的还是量子法工具），也不具诊断力，已废弃。
