# 空闲 0% CPU：现状、可行性评估与代价

> 本文只做**现状与可行性评估**，不是实施方案。若决定动手，另出 `docs/plans/NN-*.md`。
> 所有数字均为本机实测（i5-13600K，标称 3494 MHz；debug 构建；1 个栅栏、155 个图标、
> 1 个链接存储栅栏）。

## 0. 结论先行

| 问题 | 结论 |
| :-- | :-- |
| 现在空闲真的是 0% 吗？ | **不是**。进程级约 **0.15%**（真实周期计数），文档与代码注释宣称的 0% 不成立 |
| 这 0.15% 是谁的？ | 我们的 4s 库同步心跳约 **0.10%**；一个平台后台线程约 **0.05%** |
| 我们的代码干净吗？ | **主线程在空闲期已经是精确 0**——心跳之外一次都不醒（本轮动画改造的直接成果） |
| 能做到真正的 0% 吗？ | **进程级不可达**（平台线程关不掉）；**主线程级可达**（去掉 4s 心跳即可） |
| 值不值得做？ | 为省电**不值**；为「同步延迟 4s → 近乎实时」**值得**。建议先做低成本的降频，事件驱动留待有明确需求时 |

## 1. 现状

### 1.1 先纠正一个测量错误

早前用 `GetProcessTimes` 测出「4 秒 16ms、0.39%」，并据此推断心跳耗时 16ms——**这个推断是错的**。

15.6ms 是 Windows CPU **计账的一个时钟量子**（与 §2 的定时器栅格同源）。进程真实只跑了
1~2ms，是否被记成一整个量子，取决于时钟中断有没有恰好落在它运行期间。后果有两个：

- 数值被**高估 2~3 倍**（量子法 0.31%~0.52%，周期法实测 0.124%~0.149%）；
- 尖峰数量逐轮浮动（同一负载下有时记 6 次、有时记 4 次），容易被误读成"负载在变"。

正确工具是 `QueryProcessCycleTime` / `QueryThreadCycleTime`：按上下文切换时的 RDTSC 累加，
精度到周期级，且**不受量子影响**。本文所有数字均来自它。

### 1.2 空闲期的全部非零来源

进程共 **60 个线程**（WinRT / COM / DirectX 引入），其中 **58 个周期增量为精确 0**，
只有 2 个在消耗：

| 线程 | 占比 | 形态 | 归属 |
| :-- | :-- | :-- | :-- |
| `tid=65004`（窗口线程 = 主线程） | 61.7% | **除心跳外每一桶都是 0.000M**；仅在 4s 心跳处跳到 9~18M 周期 | 我们的代码 |
| `tid=11276` | 38.0% | 稳态 ~0.8~0.96M 周期 / 500ms，**与心跳无关、无周期性** | 平台（身份未确认，见下） |

500ms 细粒度采样（单位 M 周期）：

```
时间(s)   主线程 65004   后台 11276
  0.0       0.000M        0.839M
  0.5       0.000M        0.961M
  1.0      17.809M  <<<   0.951M      ← 4s 心跳
  1.5       0.000M        0.887M
  ...
  5.0       9.118M  <<<   0.732M      ← 4s 心跳
  7.5       0.000M        0.871M
```

折算成占用（3494 MHz）：

| 来源 | 周期/秒 | 占用 | 能否消除 |
| :-- | :-- | :-- | :-- |
| 4s 库同步心跳（主线程） | ~3.42M | **≈0.098%** | ✅ 可消除 |
| 后台线程 `tid=11276`（稳态） | ~1.70M | **≈0.049%** | ❌ 非我们所有 |
| 其余 58 线程 | 0 | 0% | — |
| **合计** | ~5.12M | **≈0.147%** | 下限 ≈0.049% |

单次心跳实测 **9.1M ~ 17.8M 周期（2.6 ~ 5.1 ms）**，波动接近 2 倍（疑与目录项缓存冷热有关）。

### 1.3 心跳到底在做什么

`OverlayEvent::SyncLibrary`（4s）→ `reconcile_fences`（`crates/app/src/file_ops.rs`）：

1. `reconcile_library`：遍历内存里全部图标，对「位于内部库」的每个图标调 `Path::exists()`
   → **每个图标一次 `GetFileAttributesW` 系统调用**（当前 155 个图标）；
2. `mirror_linked_fence`：对每个带 `storage_path` 的栅栏做一次 `read_dir` 比对集合，
   集合相同即返回（代码注释里已写明这是"廉价快路径"）。

即成本 ≈ `O(库内图标数)` 次 stat + `O(链接栅栏数)` 次 read_dir，**随数据量线性增长**。
当前规模下每 4 秒约 3~5ms；图标上千、链接栅栏十几个时，这个数字会明显变大——
**这是本次评估里唯一会随时间恶化的问题**。

## 2. 真正的空闲 0% CPU：可行性

先分清三个层次，否则讨论必然鸡同鸭讲：

### L1 · 主线程空闲 0 —— **已达成**

心跳之外，主线程每一桶都是 `0.000M`。消息循环是纯阻塞 `GetMessageW`，动画结束后
`CancelWaitableTimer` + `ARMED=false`，没有任何周期性唤醒。这一层不需要改动。

### L2 · 进程空闲 0 —— **不可达**

`tid=11276` 稳态消耗 ~0.049%，与心跳无关、无周期性，看起来像 WinRT / COM / DirectX
的常驻工作线程。**未确认身份**（无符号、未做栈采样；确认方法是 ETW 或 `NtQueryInformationThread`
取入口模块，本次未做）。

只要进程持有 WinRT 合成器与 COM 公寓（本项目实时背景模糊的前置条件），这类线程就在。
要消掉它，等于放弃 WinRT 合成 —— 与项目的核心视觉特性冲突。**判定为不可达。**

### L3 · 系统级「不阻止深度节能」—— **这才是真正的代价所在**

0.049% 看上去微不足道，但**一个持续有事的线程会让 CPU 无法进入深度 C-state**。
在笔记本上，对续航的影响远大于 0.05% 这个数字所暗示的量级。

残酷的事实是：**只要 L2 那 0.049% 还在，我们把自己这份 0.098% 减到 0 也换不回深度 C-state。**
这大幅折损了"为省电而改造"的收益——这是我对整件事最重要的判断。

### 2.1 去掉 4s 心跳的技术选项

| 方案 | 机制 | 覆盖 | 主要风险 |
| :-- | :-- | :-- | :-- |
| A. `ReadDirectoryChangesW` | 目录变更事件（可含子树） | 仅本地文件系统可靠 | 网络盘/可移动盘不可靠；缓冲区溢出需全量重扫；句柄随目录数增长 |
| B. `SHChangeNotifyRegister` | Shell 级变更通知 | 覆盖资源管理器操作，网络盘也常生效 | 只通知"发生了什么"，仍需自行对账；对非 Shell 发起的写入可能漏 |
| C. 自适应降频 | 保留轮询，条件化改周期 | 全覆盖 | 同步延迟变长 |
| D. 保持现状 | 4s 轮询 | 全覆盖、自愈 | 0.098% 常驻 + 延迟 4s |

## 3. 实现代价

### 3.1 方案 A（事件驱动）的具体代价

**必须解决的复杂度：**

1. **句柄与线程模型**：每个被监听目录一个句柄 + 重叠 I/O。可以复用本轮刚建好的
   `MsgWaitForMultipleObjectsEx` 基础设施，在主线程等事件（契合仓库"单线程轻量"约束，
   无需新线程）；但这意味着消息循环的等待对象从 0~1 个变成 0~N 个，循环要重构。
2. **缓冲区溢出**：`ReadDirectoryChangesW` 溢出时事件丢失且**没有"你漏了多少"的信息**，
   只能退化为全量重扫——必须实现重扫路径，等于把现有逻辑换个触发时机，省不掉。
3. **目录消失**：链接文件夹被删、改名、U 盘拔出、网络盘断连，监听句柄会失效，
   需要探测与重建；重建期间又回到轮询。
4. **事件风暴**：批量复制/删除会一口气涌进成百上千条通知，需要去抖与合并，
   否则会把省下的 CPU 一次性吐回去（还会引发大量 `DesktopItem` 构建与重绘）。
5. **正确性风险的性质变了**：今天是"最多延迟 4s，一定自愈"；改事件驱动后是
   "实时，但**可能永久漏**"。漏事件表现为栅栏里留着已被删除的图标——用户可见的 bug。
   因此**无论如何都要保留一条低频对账兜底**（例如窗口可见时 60s 一次），
   也就是说轮询逻辑不会真的被删掉，只是被降频。
6. **仍需全量扫描的时机**：启动、睡眠恢复、监听重建。

**收益：**

- 空闲占用 0.147% → 约 0.049%（**绝对量极小**，且换不回深度 C-state，见 L3）；
- 同步延迟 4s → 近乎实时（**这是唯一可感知的收益**）；
- 消除 §1.3 那个"随图标数线性增长"的隐患。

### 3.2 方案 C（自适应降频）的代价

改动集中在 `crates/app/src/file_ops.rs` 与一处常量，风险极低。可做的组合：

- 无链接栅栏且无可见变化时把周期从 4s 放宽到 30~60s；
- 按图标数动态决定周期（数据量大时反而更该放宽——注意§1.3 的增长方向）；
- 窗口不可见/系统进入省电模式时暂停。

代价：同步延迟变长。但"外部删除文件 → 栅栏项消失"延迟 30s 与 4s，体感差别很小。

### 3.3 我的判断

**为省电不值得做 A，为"同步实时"值得做 A。**

理由是 L3：平台线程那 0.049% 是深度 C-state 的地板，我们这份 0.098% 减掉后，
电池层面几乎拿不到回报。**如果目标是省电，先去确认 `tid=11276` 是什么、能不能关——
那才是真正的杠杆**（不过我判断它是 WinRT 合成的伴生线程，大概率关不掉，
那就等于承认：这个架构下"空闲 0% CPU"这条约束本来就做不到字面意义的 0）。

如果目标是体验，A 的收益（4s → 实时）是用户能感知的，但代价是引入一整套
失效/降级/去抖逻辑，属于典型"用复杂度换延迟"的交易，应该单独出 plan 并做对抗性审查。

## 4. 建议的处置顺序

1. **先改文档措辞**（零风险，消除误导）：
   `crates/render/src/lib.rs` 的「无刷新定时器」与 AGENTS.md 的「禁止常驻轮询定时器」
   应改为可验证的表述，例如「主线程空闲期无任何周期性唤醒（实测周期增量 0）；
   进程空闲约 0.05%，来自 WinRT/COM 平台线程，非本工程所有」。
2. **做方案 C**（约半小时工程量）：心跳条件化降频，顺带缓解 §1.3 的线性增长。
3. **方案 A 留待有明确需求时**（用户抱怨同步延迟 / 要把电池影响做实），
   届时单独出 plan + 独立审查。
4. **可选：确认 `tid=11276` 身份**（ETW 或取线程入口模块），它决定了 L2/L3 的下限到底能不能动。

## 5. 复现方法

```bash
# 周期级精度测单次心跳（.workbuddy-ai/，测完可删）
SYLVA_AUTOSTOP_MS=70000 ./target/debug/sylva.exe &
sleep 12
python .workbuddy-ai/sync_cost.py 120        # 250ms 分桶，输出各桶周期数

# 按线程拆分空闲负载，看是谁在耗
python .workbuddy-ai/thread_cycles.py        # 10s 采样，按线程列出周期增量与占比

# 主线程 vs 指定后台线程的 500ms 细粒度对照（最能说明"谁在轮询"）
python .workbuddy-ai/thread_detail.py 11276  # 参数为待对照的后台 tid

# 空闲 0% 回归（量子法，够粗但快）
python .workbuddy-ai/cpu_probe.py            # 空闲 → 连续开合 → 再空闲，三窗口对比
```

判据（回归用）：

- 主线程在**非心跳桶**必须精确为 `0.000M`；
- 首尾两个空闲窗口的周期增量应**完全相等**——不等即说明有周期性唤醒残留。
