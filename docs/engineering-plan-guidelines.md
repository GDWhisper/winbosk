# 工程实施计划（Plan）编写指南与规范

本规范定义了软件开发、架构重构及复杂功能实施计划（Implementation Plan）的编制标准与审查准则。所有实施计划必须具备**严格分层、因果建模、动力学推演与可验证性**。

---

## 一、核心设计原则（Core Principles）

1. **因果状态建模，而非任务罗列**：Plan 的核心是定义系统状态如何变迁、数据流如何闭环，禁止仅罗列文件路径和增删函数。
2. **单向依赖自底向上**：改动必须严格按依赖拓扑自底向上实施（`底层领域模型/核心算法 → 适配与驱动层 → 组装与交互层`），禁止反向或越级引用。
3. **默认极简与高级解耦**：基础操作必须无模态阻断、即时生效；重型配置与高摩擦逻辑必须降级为可选分支，严禁作为前置强约束。
4. **隐性动力学优先推演**：必须前置分析新逻辑与系统内既有常驻机制（定时器、事件循环、文件监视、数据同步、缓存）的交互边界。
5. **纯算法与平台隔离**：核心业务与算法逻辑必须抽离为无外部 I/O、无平台特定依赖的纯函数/数据模型，保证能在内存中瞬时完成单元测试。

---

## 二、实施计划必备结构规范（Structure Specification）

每一个实施计划必须按以下六个标准章节组织：

```markdown
# [特性/重构名称] 实施计划

## 1. 目标与非目标 (Goals & Non-Goals)
- **Goals**：明确本次改动必须交付的核心价值与行为改变。
- **Non-Goals**：明确本次改动严格排除的范围与不应触碰的架构边界。

## 2. 状态契约与接口设计 (Contracts & Data Models)
- 给出新增/修改的核心数据结构定义（Struct/Enum/Class 签名）。
- 明确定义输入参数、输出报告结构（禁止使用歧义布尔值，必须使用具名结果结构）。
- 明确单位口径与物理度量基准（坐标系、DPI、时间基准、所有权规则）。

## 3. 隐性机制与系统动力学推演 (Hidden Dynamics Analysis)
- **常驻后台与同步引擎**：新状态如何被既有的轮询、文件监视、后台同步识别？
- **空闲性能约束**：操作完成后系统能否立即回到 0% CPU 与 0 磁盘 I/O？
- **孤儿与物理变更回流**：外部物理实体被删除/重命名时，新容器如何感知与清理？

## 4. 分层改动清单 (Implementation Steps)
- 按「底层 Core/Model → 驱动适配/渲染 → 上层组装/交互」顺序，逐层列出受影响文件、改动意图与实现要点。

## 5. 防御性自查清单 (Defensive Invariants)
- 对照标准自查清单，逐项给出针对性防御设计。

## 6. 验证与交付门禁 (Verification Gates)
- 自动化单元测试命令与用例矩阵。
- 静态分析阻断项（零警告）。
- 独立干净上下文的代码审查要点。
```

## 三、隐性动力学自查六律（The 6 Invariants）

在定稿 Plan 前，必须强制逐项通过以下六条红线自查：

| 序号 | 校验律 | 检验准则与阻断条件 |
| :---: | :--- | :--- |
| **1** | **常驻后台冲突律<br>(Daemon Invariant)** | 检查系统是否存在周期性定时器、轮询或双向同步引擎。<br>**规则**：实体跨容器移动或重新分类后，全局事实来源必须保持一致。严禁局部容器视角的“缺失”误判导致后台循环重注册、内存泄露与磁盘常刷。 |
| **2** | **空闲性能归零律<br>(Zero-Idle Invariant)** | 检查是否有未休眠的轮询定时器，以及事件处理后的重绘门控。<br>**规则**：一切批处理、分类、整理或动画结束后，系统必须立即回到 0% CPU 占用与无 I/O 状态。禁止无实质状态变更的静默重绘与重写。 |
| **3** | **孤儿状态回收律<br>(Orphan Invariant)** | 检查实体在外部物理存储/数据源发生异步变动（删除、重命名、截断）时的感知链路。<br>**规则**：无专属镜像路径的收纳容器，必须接入统一的实体有效性比对通道，杜绝残留无法访问的“幽灵项”。 |
| **4** | **语义精准定位律<br>(Semantic Invariant)** | 检查代码中是否存在通过下标索引（如 `first()`、`[0]`）假定实体角色的逻辑。<br>**规则**：严禁用位置假设替代语义检索。定位关键实体必须基于稳定特征（唯一标识、类型、路径或名称），并提供完整的回退处理。 |
| **5** | **状态全集校验律<br>(Compound State)** | 检查针对配置项、规则或实体的有效性判断逻辑。<br>**规则**：严禁仅依据配置值（如 `preset.is_some()`）判定有效。必须严格校验复合生命周期状态（如 `enabled && !is_deleted && valid`），防止非活跃规则截断正常流程。 |
| **6** | **旁路数据对齐律<br>(Sidecar Invariant)** | 检查主数据容器是否有平行的旁路缓存（如布局高度、命中模型、索引表）。<br>**规则**：增删主数据项时，必须在同一事务中同步更新旁路结构（`push`/`remove`/`resize`），严禁跨帧延迟更新导致越界或算法入参失真。 |

## 四、验证与审查交付规范（Verification & Review）

1. **测试用例覆盖标准**：
   - 零输入/空集合场景：必须返回明确的空报告，不得崩溃或执行无意义 I/O。
   - 幂等性场景：相同操作连续执行两次，第二次必须为 0 变动、0 创建、0 移动。
   - 空间互斥断言：新增与排布操作完成后，几何坐标严格无重叠。
2. **静态质量门禁**：
   - 静态检查强制零警告（`-D warnings`），包含死代码、类型转换与条件分支冗余。
   - 全局格式化一致性（`--check`）。
3. **独立上下文子代理审查规范**：
   - 实施完成后，必须启动**无此前对话历史与思维偏见的独立子代理**。
   - 审查重点：**对抗性代码走查**（并发安全、后台循环交互、内存单调膨胀、外部删除回流、边界值溢出）。
