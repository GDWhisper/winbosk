# 加载器锁死锁：根因取证与诱发面收窄 实施计划

> **本文件自包含**：不依赖任何会话上下文即可实施。写法对齐 `docs/plans/11-hang-resilience-and-ime-scope.md`
> 与 `docs/plans/12-exit-teardown-stall.md`：§0 是实测 ground truth，§1-§6 是契约与门禁。
> 若与 `AGENTS.md` 冲突，以 `AGENTS.md` 为准。

## 0. 背景与现场结论（ground truth，2026-09-28 实测）

plan 11（假死韧性）与 plan 12（退出收尾限时兜底）落地后，**假死的家族性根因**仍未定位：
三次独立现场（含 plan 11 的原始事件）指向同一形态——**Windows 加载器锁（loader lock）被长期占用**，
一切需要它的操作全部排队长眠：`LoadLibrary` / `LdrGetDllHandleEx`（加载）、`LdrInitializeThunk`
（新线程启动）、`LdrShutdownThread`（线程退出）。

| # | 现场（转储） | 主线程卡点 | 伴生形态 |
| :---: | :--- | :--- | :--- |
| 1 | `pid27040`（plan 11 原始事件，release 实例点击后冻结） | `ntdll!ZwWaitForSingleObject`（无名 Event）← `MSCTF/imm32` ← `user32`；栈含 `RTSSHooks64!RTSSCBTProc` | 进程 49 线程全 Wait |
| 2 | `pid65708`（收尾期，`已退出` 后不散） | `nvwgf2umx → RtlFreeHeap` 等待（GPU 释放路径内） | **14 线程卡 `LdrShutdownThread`**（含 tracing-appender、多枚系统线程）；**3 线程卡 `LdrInitializeThunk`**——含当时收尾期新建的 `winbosk-exit-deadline`（创建了但**永不启动**，T1/T2 全失效） |
| 3 | `pid66588`（启动 ~2.4s，**从未进入收尾**） | `USER32!User32InitializeImmEntryTable → LdrLoadDll`（user32 的 IMM 惰性初始化在加载 DLL 时等锁） | `winbosk-menu-prime`（外壳扩展预热线程）卡在 `windows.storage.dll / SHCORE!SHCreateThread`（`SHCreateShellItemArrayFromIDLists` 一线）且**数分钟不前进**；4 线程卡 `LdrShutdownThread`、1 线程卡 `LdrInitializeThunk` |

- **复发率**：2026-09-28 实测约 **1/4**（18 次冒烟 4 次复发；plan 11 时期约 1/3）。同一二进制、同样命令，
  其余运行干净退出 → 非确定性死锁。
- **已排除**：非业务代码死锁（现场 2 主线程在 GPU 释放、现场 3 在 IMM 初始化，均不与业务锁交集）；
  非 plan 12 收尾机制引入（其 T2 在收尾期现场 2 形态下仍能 45s 清场，见 plan 12 §7.1）。
- **本机环境特征**：Win11 26200 / 150% DPI / NVIDIA 驱动（`nvwgf2umx`）/ **RTSS 注入 `RTSSHooks64.dll`**
  （RivaTuner Statistics Server）/ 签名校验组件线程（crypt32、wintrust）也在 `LdrShutdownThread` 挂起名单里。
- **危害分级**：
  - 收尾期复发（现场 2）：plan 12 的 T1/T2 已闭环清场（进程必散、图标兜底恢复、单实例互斥释放）。
  - **收尾前复发（现场 3）：无自动恢复**——僵尸占互斥 + 桌面图标隐藏，用户"双击无反应"，
    只能任务管理器结束（看门狗 30s error 日志已留痕可定位）。
- **两处可直接复用的现场资产**：转储 `%TEMP%\winbosk-hang-20260928-pid{27040,65708,66588}.dmp`；
  只读取证工具箱（栈采样 / 线程名 / 转储 / 图标恢复）见 plan 12 §7 与项目记忆 `debug-hung-process-toolkit`。

## 1. 目标与非目标 (Goals & Non-Goals)

### Goals

- **G1 定位持锁者**：用已有三个转储回答——加载器锁当前由哪个线程持有？该线程栈顶落在哪个模块的
  什么回调（`DllMain` / `DLL_THREAD_ATTACH|DETACH` / 其它）？是**自持不自放**（DllMain 内死等）
  还是**持锁线程本身在等本进程的其它线程**（环路）？
- **G2 A/B 收窄诱发面**：把可疑并发面逐个关闭，各跑 N=20 次冒烟统计复发率，找到使复发率显著变化的因子。
  候选因子（按嫌疑排序）：
  1. **外壳扩展预热线程 `prime_startup`**（`crates/app/src/shell_menu.rs`）：现场 3 的唯一非常规伴生线程；
     其内部走 `CoCreateInstance`/Shell 扩展装载（`LoadLibrary` 密集）；
  2. **RTSS 注入**：用户侧退出 RTSS 后重复 N 次（对照实验，无代码改动）；
  3. **IME/IMM 面**：进消息循环前的 IMM 惰性初始化时机（现场 3 主线程卡点），
     与 plan 11 的 b（关联收窄）之后的残余入口；
  4. **线程退出时序**：调试钩子线程（`WINBOSK_AUTOSTOP_MS` 用的一次性线程）与后台线程在收尾期集中退出的时序。
- **G3 按证据选修复**：优先「**删除/收窄诱发动作**」（如预热改惰性、限流、移出启动窗口），
  其次「规避第三方注入面」；**禁止**引入轮询、重试、超时加锁类补丁（与约束 10 冲突）。
- **G4 回归口径**：修复后 **30 次冒烟 0 复发**为目标；若无法归零，产出"残余复发率 + 触发条件 +
  危害定级"结论并回写 plan 12 §7.4。

### Non-Goals

- **不动 plan 12 的收尾兜底**（T1/T2 已闭环收尾期清场）；**不把 T2 扩展到运行期**——
  主线程存在合法的长同步 I/O（大目录拖入复制），运行期强杀有破坏性（plan 11/12 明确"不做自动恢复"）。
- 不改 `crates/core`（零 OS 依赖）；不引入新进程、新运行时、外部监视器。
- 不逆向 RTSS / NVIDIA 驱动内部（第三方注入只做"存在性证据 + 规避实验"）。
- 不重新打开 d2（自动落 minidump）：本计划用既有转储与手动工具箱（用户已拍板 d2 不做）。
- 不修改 WorkerW/Progman 拓扑与 `IconGuard` 守卫语义（`AGENTS.md` 约束 3）。

## 2. 取证与实验契约 (Contracts)

### 2.1 转储分析口径（G1 输出，具名三问）

对每个转储回答并记录：

```
持锁线程 tid = ?            // 栈中处于 LoadLibrary/DllMain/激活上下文 一线的线程
持锁栈顶函数 = ?            // 解析到"模块!函数"级（Rust 内部帧不可解析时给出模块与偏移）
持锁性质 = 自持不自放 | 环路（持有者等待本进程其它线程，给出等待对象 tid）
```

工具（全部只读，流程见 plan 11 附录 B 与 plan 12 §7）：
- `WinDbg`（若有）：`!analyze -v`、`~*k`、`!cs -l`；重点看 `ntdll!LdrpLoaderLock` 的持有者。
- 无 WinDbg 时：`python /tmp/sylva-allthreads.py <pid>` + `pwsh -File target/tmp-threadnames.ps1 <pid>`
  交叉出"无名栈 ⇄ 具名线程"；用 `sylva-makedump.py` 留存新现场。

### 2.2 A/B 实验方法（G2）

- **单变量**：每档只改一个因子，其余全同（同二进制、同命令、同机器状态）。
- **N=20 次/档**：`WINBOSK_AUTOSTOP_MS=1200` 连跑；**复发判定 = wall > 20s**（正常 ~4s±1s；
  收尾期复发会被 T2 在 45s 清场、收尾前复发需手动清理——脚本须自动：超时 → 采样+清理+恢复图标）。
- **记录结构**：`{档位, 复发次数/20, 每次的 main 栈顶模块, phase 字段, 是否进入收尾}`。
- 实验用开关一律 `env` 变量 + `TEMP-VERIFY` 注释，实验结束必须 `grep -rn TEMP-VERIFY crates/` 清残留。

### 2.3 修复选型准则（G3 输出）

每个候选修复给出具名三元组，禁止歧义布尔：

```
候选: {行为改变一句话}
复发率: {前→后, N=30}
启动代价: {ms 或 "无"}       // 用现有 "内存快照/就绪" 日志时间差量
首次右键代价: {ms 或 "无"}    // 仅当触及 shell_menu 时实测（预热的目的就是它）
```

## 3. 隐性机制与系统动力学推演 (Hidden Dynamics Analysis)

- **常驻后台与同步引擎**：唯一相关的常驻源是 4s `SyncLibrary` 心跳与预热线程（一次性）。
  预热的任何"延迟/限流"改法**不得引入新周期源**（约束 10 判据：主线程非心跳桶精确为 0，
  实测方法见 plan 12 §7.1：`QueryThreadCycleTime` 按线程 60s 增量）。
- **空闲性能归零**：A/B 脚本与取证全部在进程外（只读采样），不影响被测进程的 CPU 口径。
- **孤儿状态回收**：复发僵尸会占单实例互斥 + 图标隐藏——实验脚本必须带清理与
  `target/tmp-restoreicons.ps1` 恢复，避免实验期间桌面停留在坏状态。
- **语义精准定位**：复发判定只用 wall 时间 + 日志 + 线程样本；**显式禁用** `Responding` 与
  顶层窗口枚举（plan 12 §0/§7.3 已证伪其判据地位）。
- **状态全集校验**：`prime_startup` 若加开关，校验必须复合（`enabled && 线程存活 && 未完成`），
  禁止只看单个布尔（六律 5）。
- **旁路数据对齐**：本计划无主/旁路数据结构变更（纯取证 + 收窄），无跨帧对齐面。

## 4. 分层改动清单 (Implementation Steps)

> 本计划**先取证后改动**：阶段 A 无业务代码改动；阶段 B 的改动内容由 G1/G2 证据决定，
> 以下给出按嫌疑排序的候选与各自的回退开关设计。

1. **阶段 A（取证，零业务改动）**
   - A1：按 2.1 分析三个转储（若需新现场，先跑冒烟复现 → 采样/转储 → 再清理）。
   - A2：按 2.2 跑基线档（不改任何行为）20 次，记录本机当前复发率与栈顶分布。
   - A3：对照档：用户退出 RTSS 后重复 A2（需用户配合；只读，不改代码）。
2. **阶段 B（按证据收窄，候选按嫌疑排序）**
   - B1（预热门 · 首选）：`prime_startup` 收窄。候选实现（按优先级）：
     ① **惰性化**：不在启动期预热，改为主线程空闲时一次性触发（触发器必须复用既有事件，
     不得新建定时器）；② **限流**：每次仅预热 1 个扩展、间隔完成（一次性链，非周期）；
     ③ **延迟 T 秒**：挪出启动窗口（证据不足时不选——未消除根因只是降低窗口）。
     回退开关：`WINBOSK_NO_PRIME=1`（TEMP 期）→ 定稿后为配置项或直接删除。
   - B2（IME 面）：若证据指向 IMM 惰性初始化与其它加载并发——把触发点从启动窗口挪到
     用户交互之后（如首次 `focus_for_input` 前不触及 IMM 面）；与 plan 11 b 的既有约定保持一致。
   - B3（线程退出面）：若证据指向线程退出风暴——收尾前先向辅助线程发出停止信号并等其
     退出（有界等待），避开与主线程释放链的加载器锁竞争。
3. **core 层**：无改动（明确声明）。渲染层只在 B3 触及（若需），默认不动。

## 5. 防御性自查清单 (Defensive Invariants)

| 律 | 针对性防御 |
| :--- | :--- |
| 1 常驻后台冲突 | 预热收窄的所有候选都是一次性链或惰性触发；严禁周期重试；不动 4s 心跳/库同步 |
| 2 空闲归零 | 新代码只在启动/交互窗口执行一次；空闲口径用 `QueryThreadCycleTime` 按线程实测（plan 12 §7.1 方法） |
| 3 孤儿回收 | 实验脚本自带清理 + 图标恢复；修复不新增文件类型；转储按"最近 3 份"约定清理 |
| 4 语义精准 | 复发判定 = wall 时间 + 日志（phase）+ 线程样本；禁用 `Responding`/窗口枚举 |
| 5 状态全集 | `prime` 开关/惰性触发条件用复合校验（enabled && 未完成 && 线程态），禁止单布尔 |
| 6 旁路对齐 | 无主/旁路数据结构改动；若 B3 引入线程停止信号，信号与线程生命期的读写顺序须显式（Release/Acquire） |

## 6. 验证与交付门禁 (Verification Gates)

自动化门禁（全绿为交付前提；**不并行跑 cargo**；先退出运行中的实例）：

```powershell
cargo build --workspace
cargo test --workspace
cargo clippy --workspace -- -D warnings
cargo fmt --all -- --check
```

静态断言：

- `grep -rn "TEMP-VERIFY" crates/` → 实验开关全部清除（空输出）。
- `grep -n "TEMP-VERIFY\|WINBOSK_NO_PRIME" crates/` → 定稿后仅允许存在正式配置项，不得留临时 env 名。
- 若触及 shell_menu：`grep -n "Builder::new" crates/app/src/shell_menu.rs` → 预热线程仍为一次性，无循环。

实验门禁（G2/G4 的核心判据）：

| # | 操作 | 期望 |
| :---: | :--- | :--- |
| 1 | 基线档 20 次冒烟 | 复发率记录在案（作为对照；当日 ~1/4） |
| 2 | 候选修复档 30 次冒烟 | 0 复发（未达则记录残余率与栈顶，回写 plan 12 §7.4） |
| 3 | 空闲 5 分钟 | 唤醒口径与改动前一致（按线程 cycles 判据） |
| 4 | 首次右键菜单 | 若动预热：首次右键延迟实测不劣化（记录 ms） |
| 5 | 编辑期中文输入（人工） | 若动 IME 面：组合/上屏/候选窗正常（沿用 plan 11 待人工项） |
| 6 | 退出必散 ×20 | `Get-Process winbosk` 无输出；复发时 T1/T2 行为符合 plan 12 契约 |

对抗性审查要点（**独立干净上下文子代理**，实施完成后必须执行）：

- 收窄/惰性化是否引入新的周期唤醒或"永远不预热"的退化（首次右键延迟是否可接受）。
- 删除或延迟预热是否让"首次右键卡顿"回归（plan 05 的既有约束：Shell 扩展首次加载可卡数秒）。
- 若动线程停止信号：收尾路径新增有界等待是否与 plan 12 的 T1/T2 时序冲突（15/45s 预算内）。
- 实验开关清理后，行为是否与实验档一致（防止"只在实验条件下不复发"）。
- 修复的回退面：出现新问题时如何一键回退（配置项或 revert 范围是否最小）。
